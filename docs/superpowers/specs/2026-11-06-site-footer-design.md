# Shared site footer — design

The door has a footer; nothing else does. A visitor who lands on the calculator from a QR code, or on MiCar Shop from a search, has no map of the site below the top strip. This work moves the door's footer into `packages/brand`, extends it, and renders it on six pages, in English and Spanish, with a test that every link goes somewhere real.

## What the visitor sees

Four columns on a wide screen. On a phone (720px and under) the MiCar column spans the width and the other three sit in two columns below it. A legal line runs under the columns.

| Column (EN / ES) | Links (EN / ES) | Goes to |
|---|---|---|
| **MiCar** / MiCar | Home / Inicio | `SITE_URL` |
| | the blurb (not a link) | |
| **Value** / Valor | Value a car / Calcular el valor | `${SITE_URL}#/value` |
| | Window sheet / Hoja de ventana | `${SITE_URL}#/sticker` |
| | The grade / La calificación | `${SITE_URL}#grade` |
| **World** / Mundo | MiCar World / MiCar World | `WORLD_URL` |
| | Enter the Strip / Entra al Strip | `${WORLD_URL}strip` |
| | MiCar Shop / MiCar Shop | `SHOP_URL` |

| **About** / Acerca de | How it's built / Cómo está hecho | `https://github.com/lasting-oasis/Micar-com` (new tab) |
| | Keyholder / Keyholder | `${SITE_URL}#keyholder` |

- **Blurb:** "Said MEE-car. One brand: the value, the card, the garage, the world. Charlotte, NC." / "Se dice MI-car. Una marca: el valor, la tarjeta, el garaje, el mundo. Charlotte, NC."
- **Legal line:** "© {year} MiCar" and "Values are estimates, not appraisals or offers to buy." / "Los valores son estimaciones, no avalúos ni ofertas de compra."

The look is the door's current footer: Barlow Condensed uppercase, paint-yellow column titles, haze for secondary text, paint on hover, on the night background.

## Where it appears

| Page | Placement |
|---|---|
| Door | Replaces the `.foot` columns and `.legal` line. The giant MiCar wordmark stays, door-only, below the shared footer. |
| Calculator (`#/value`) | Full width at the bottom of the page. See "Page shape" below. |
| Car page (`#/c/…`) | Full width at the bottom of the page, in `Shell`, so the "this link doesn't point to a car" notice gets it too. See "Page shape" below. |
| World setup screen | Last child of the `h-[100dvh]` scrolling container, after the two-column grid. |
| Shop gateway (`/shop`) | After the existing `shop.footer` line, which stays. |
| Garage placeholder (`/garage/`) | Generated by `pnpm site` (see below). |

**Not on:** the window sheet builder (`#/sticker`), the printed sheet, 3D views, the Strip entry card (`/strip`). The footer is hidden in print on every page.

## Decisions

1. **The footer's text lives with its links.** `DOORS` holds English labels and each app translates them; the footer holds `{ en, es }` pairs instead. There are three renderers, one of them a static page with no dictionary, and a single source keeps them from drifting. Most of the Spanish is the door's existing copy. The exceptions: "Inicio" is new, "Garaje" is new to the footer, "Entra al Strip" comes from the World's setup button, and "Cómo está hecho" is decision 2.
2. **"How it's built" becomes "Cómo está hecho".** The value dictionary maps it to "Cómo se calcula" ("how it's calculated"), which is wrong for a link to the source code. The door's footer was the only caller of that entry, so it becomes unused; unused dictionary entries are harmless and it is left in place.
3. **Footer links are absolute, like the strip's.** They are built from `SITE_URL` and `WORLD_URL`, so the same data works on both hosts. The door's current footer used `calculatorUrl()`, which follows the current host. The cost is the one the strip already has: on a local dev server, footer links go to production.
4. **Garage goes to `/garage/`.** It is the page that says the Garage is opening soon, and nothing else links to it. The strip's Garage door still goes to `#card` on the door; the two are reconciled when the Garage launches.
5. **The © year is computed**, at render in the apps and at build time on the static page, which rebuilds on every deploy. A hard-coded 2026 goes stale in January.
6. **The World setup screen keeps its language key.** Value stores `nexus.lang` and the World stores `cds_lang`. They are on different hosts, so they cannot share one; this work does not change that.
7. **Windows-only build quirks are not fixed here.** See "Out of scope".
8. **The Spanish link says "Entra al Strip", not "La Pista".** The door calls the place "La Pista" and the World's setup button says "Entra al Strip". The footer matches the button, because that is what the link does and where it lands (`/strip`). The World's setup screen already uses both words. Settling on one name across the site is separate copy work.

## The bug this depends on: section links land at the top

`Router` in `apps/value/src/main.tsx` calls `window.scrollTo(0, 0)` on every `hashchange`, and nothing scrolls to a section when the page loads. Measured on the live site on Nov 6, 2026: clicking the door's "The grade" link ended at scroll 0 with the section 2,264px below, and loading `/#grade` directly did the same. Today's strip `#card` link has the same fault, and it would make two of the new footer's links useless, so the fix is part of this work.

**The fix:**

- A new side-effect-free module, `apps/value/src/route.ts`, mirrors `apps/sim/src/route.ts`. `main.tsx` calls `createRoot` when imported and value's tests run in Node with no `document`, so the pure logic has to live outside it. It exports two functions:
  - `routeFromHash(hash, search)` returns `{ view: 'car' | 'sticker' | 'value' | 'door', code? }`, using the regex and checks now in `Router`.
  - `sectionFromHash(hash)` returns the id for a plain anchor (`#grade`) and `null` for a route (`#/value`, `#/c/abc`) or an empty hash.
- `Router` scrolls in a `useLayoutEffect` keyed on `hash`, after the new page has rendered. If `sectionFromHash` names an element that exists, it scrolls to that element. Otherwise, if the hash differs from the previous one (compared with a ref, not a once-only flag, because StrictMode runs effects twice in dev), it scrolls to the top. On first load with no section it does nothing, so the browser's scroll restoration on reload still works.
- `section[id]` on the door gets `scroll-margin-top` so the sticky 48px strip does not cover the heading.
- If late-loading fonts or images shift the section after the first scroll (checked in the browser), the scroll runs once more on `document.fonts.ready`.

A calculator URL carrying `?make=…` keeps rendering the calculator whatever the hash says (`legacyCalculatorLink`). That does not affect the footer: its absolute links carry no query string, so clicking one from such a URL is a full page load onto the door.

## How it is built

### `packages/brand`

- **`src/footer.ts`**, exported as `@micar/brand/footer`. Plain data and one function, no React:
  ```ts
  export type FooterLang = 'en' | 'es';
  type Text = Record<FooterLang, string>;
  export type FooterLink = { id: string; label: Text; href: string; soon?: boolean; external?: boolean };
  export type FooterColumn = { id: string; title: Text; blurb?: Text; links: FooterLink[] };
  export const FOOTER_COLUMNS: FooterColumn[];
  export const FOOTER_SOON: Text;
  export const FOOTER_ESTIMATES: Text;
  export function footerCopyright(year: number): string; // "© 2026 MiCar"
  export function footerHtml(lang: FooterLang, year: number): string;
  ```
- **`src/footer.css`**, exported as `@micar/brand/footer.css`. The door's rules, rewritten against the `--mc-*` tokens. It sets its own background, text colour, box sizing, link colour and safe-area side padding, because the pages sit on different resets. It includes `@media print { .mc-foot { display: none; } }`, and at 720px and under each link is at least 44px tall.
- **Every rule for something inside the footer has at least two classes**, such as `.mc-foot .mc-foot-h`, `.mc-foot .mc-foot-blurb` and `.mc-foot .mc-foot-links a`. On the door, `.dp p` and `.dp a` (specificity 0,1,1) would otherwise beat single-class rules or tie with `.mc-foot a`, and `App` loads before `Door`, so import order cannot be relied on. A bare `.mc-foot p` is not allowed, because it would also hit the column titles.
- **Column titles are `<p class="mc-foot-h">`**, not headings, so the footer adds nothing to a page's heading outline.
- **The root element is exactly `<footer class="mc-foot">`** in all three renderers. The build guard below matches on it.

### The apps

`apps/value/src/Footer.tsx` and `apps/sim/src/Footer.tsx` each render `FOOTER_COLUMNS` with that app's React and `useLang`, as `Strip.tsx` does. The markup and class names match `footerHtml`; a test pins the link list so the three cannot differ in what they point at. Value imports `footer.css` from `Footer.tsx`; the World adds it to `index.css` beside `strip.css`.

`door.css` loses `.dp footer`, `.dp .foot*` and `.dp .legal`, including the responsive overrides at lines 562–563 and 666. It keeps `.dp .wordmark`, whose wrapper in `Door.tsx` gets the `gutter` and `inner` classes the old footer provided.

### Page shape (calculator and car page)

Two things stop a footer reaching the screen edges on these pages: the wrapper's `sm:px-4` and `py-*` padding, and the padding on `body` in `apps/value/src/index.css:70-71`. A column flex container would also shrink a direct `mx-auto max-w-6xl` child to its content, which would narrow the "not a car" notice. So `App` and `Shell` both take this shape:

```tsx
<div className="flex min-h-screen flex-col">                {/* no padding */}
  <div className="w-full flex-1 py-6 sm:px-4 sm:py-10">     {/* the old padding */}
    <div className="mx-auto max-w-6xl">{children}</div>
  </div>
  <Footer bleed />
</div>
```

`bleed` adds a value-only class, defined in `index.css` rather than the shared `footer.css`, that cancels the body padding with negative side margins, using the same `max(16px, env(safe-area-inset-*))` expressions. It does not use `100vw`, which would cause sideways scrolling when a scrollbar is showing. The door renders `Footer` without `bleed`.

### The Garage placeholder

`tools/garage-placeholder.html` becomes a template with a `<!-- footer -->` marker and the same Google Fonts links as the door. Its body changes from a centred grid to a column: the three-line message centred in the remaining height, the footer at the bottom. The message stays English.

`tools/build-garage.ts` reads the template, inlines `tokens.css` and `footer.css`, inserts `footerHtml('en', year)` and a `hidden` `footerHtml('es', year)`, and writes `site/garage/index.html`. It throws if the template has no `<!-- footer -->` marker. A short inline script picks the visible footer with the same rule as value's `i18n.tsx`: `?lang=`, then `nexus.lang`, then the browser's language. With scripts off, the English footer shows.

`pnpm --filter … exec` runs in `apps/value`, while `build-site.sh` works from the repo root. So the script resolves every file (template, `tokens.css`, `footer.css`, output) from `import.meta.url`, never from the current directory. It imports `../packages/brand/src/footer.ts` by relative path; the package name only resolves there through pnpm's hoisted `NODE_PATH`.

`tools/build-site.sh` replaces the `cp` for the Garage with:

```bash
pnpm --filter @micar/value exec tsx ../../tools/build-garage.ts
grep -q '<footer class="mc-foot"' site/garage/index.html
```

The `grep` fails the deploy if the footer ever goes missing from that page. It matches the rendered tag rather than the class name, which is also in the inlined CSS. `tsx` is already a value dev dependency, so nothing new is installed.

## Tests

`packages/brand` has no test runner, so tests live in the apps that consume it.

**`apps/value/src/footer.test.ts`**

It imports from `route.ts` and never from `main.tsx`. It reads `Door.tsx` and `tools/build-site.sh` with `?raw`, following `i18n.test.ts:16`; `node:fs` would pass in vitest and then fail `tsc -b`, which compiles value's tests without Node types.

- Every link's `href` parses as a URL and starts with `SITE_URL`, `WORLD_URL` or the repo URL.
- Every `SITE_URL` link resolves:
  - `#/x` gets a non-door view from `routeFromHash`.
  - `#x` is an `id="x"` present in `Door.tsx`.
  - `/garage/` requires a non-comment line in `build-site.sh` containing `tools/build-garage.ts`. Matching on `garage` alone would pass on the comment and the `mkdir` even with the generator deleted.
- Every title, label and blurb has non-empty `en` and `es`.
- The link list is pinned to the table above, so a change to it is deliberate.
- `footerHtml` output contains every `href` and every label in the requested language, and escapes nothing into broken markup (`How it's built`).
- `sectionFromHash`: `#grade` → `grade`; `#/value`, `#/c/abc`, `#` and an empty string → `null`.
- `routeFromHash` keeps today's behaviour: each route, the `#/car/` alias for old sheets, and `?make=…` opening the calculator.

**`apps/sim/src/footer.test.ts`**

- Every `WORLD_URL` link passes through `routeFromLocation` to the expected view: `/` → `world`, `/strip` → `strip`, `/shop` → `shop`.

**Browser check, before the branch is called done**

All six pages at phone (375px) and desktop widths, in both languages: footer present, no horizontal scroll, EN/ESP switch updates it live. On the calculator and car page, including the "not a car" notice, the footer touches both screen edges and the notice stays full width. On the door, title spacing and link colour match the other pages. The window sheet builder, `/strip` and a 3D view show no footer. Print preview hides it. On a local build, `#grade` and `#keyholder` land on their sections, both by changing the hash on the door and on a fresh load (footer links go to production on a local build, per decision 3). `site/garage/index.html` from a real `pnpm site` run shows the footer.

**Before merging:**

```bash
pnpm --filter @micar/sim test
pnpm --filter @micar/value test
pnpm --filter @micar/sim exec tsc --noEmit
pnpm --filter @micar/sim build
pnpm site
```

CI does not run `pnpm site`; only the Pages job on `main` does. So the local `pnpm site` run is the only check of the Garage generator and its guard before merge. `tools/build-garage.ts` is also outside every `tsconfig`, so `tsc` does not check it. The sim's `serverWiring.test.ts` needs the fix below to report a clean pass on Windows.

## One small fix alongside

`serverWiring.test.ts` deletes its temp folder immediately after killing its server. On Windows the folder is still locked, so `rmSync` throws `EBUSY` and `pnpm --filter @micar/sim test` exits 1 with 151/151 tests passing. Adding `maxRetries: 10, retryDelay: 100` to that `rmSync` fixes it. Linux CI and the deploy are unaffected. It goes in its own commit.

## Out of scope

- **`pnpm site` on Windows.** `bash` is not on the PowerShell path, and Git Bash rewrites `BASE_PATH=/Micar-com/` into a Windows path, which breaks local asset links. Production builds on Ubuntu are fine. Local builds here set `MSYS_NO_PATHCONV=1` and add Git's `bin` folder to the path for that command.
- Sending the strip's Garage door to `/garage/`.
- Translating the Garage placeholder's three-line message.
- A footer on the window sheet builder, the `/strip` card or any 3D view.
- Unifying the two apps' language storage.
- Removing the door footer's now-unused strings from `i18n-es.ts`.
- Adding `pnpm site` to `ci.yml`.
- Choosing one Spanish name for the Strip across the site.
